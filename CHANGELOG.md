# Changelog

This file records the changes for each Koodam version. The newest version is first.

## Unreleased

### Agents

- Add the [read-only spend API](docs/spend-api.md) for Agent runs and spend by label. The binary `spend-api` serves `/v1/runs`, `/v1/spend` and `/v1/openapi.json` ([#397](https://github.com/mohanraj00/koodam/pull/397), [#393](https://github.com/mohanraj00/koodam/pull/393), [#394](https://github.com/mohanraj00/koodam/pull/394), [#395](https://github.com/mohanraj00/koodam/pull/395), [#396](https://github.com/mohanraj00/koodam/pull/396), [#398](https://github.com/mohanraj00/koodam/pull/398)).
- Export [Prometheus metrics](docs/metrics.md) for Agent counts, run time, spend and budgets
  ([#413](https://github.com/mohanraj00/koodam/pull/413)).
- Count the failed key blocks of each revoke in the metric `koodam_revoke_failures_total`, by the kind of the key owner. The chart value `metrics.serviceMonitor.enabled` adds an optional `ServiceMonitor` for the metrics Service. [docs/metrics.md](docs/metrics.md) lists each metric, and a test compares the list with the code ([#130](https://github.com/mohanraj00/koodam/issues/130)).
- Serve a read-only operations page from `spend-api` at `/`. A viewer mode checks each token with a TokenReview and shows only the namespaces where the viewer can list Agents. The page uses the pinned mugham kit, and [examples/operations-page](examples/operations-page/README.md) runs it with synthetic data ([#13](https://github.com/mohanraj00/koodam/issues/13)).
- Add the namespaced `SpendBudget` type with its CRD rules. It gives the Agent runs of a namespace a spend limit for each UTC day or month. The name must be `default`. The chart installs the CRD and a read-only viewer role, and it has no write role for users. No controller reads the type in this change. [docs/spend-budgets.md](docs/spend-budgets.md) has the API ([#420](https://github.com/mohanraj00/koodam/issues/420)).
- Apply the `SpendBudget` of a namespace to its Agent runs. The Agent controller keeps a ledger in the status: a run starts only if the settled spend and the reserved budgets of the period, with the run budget, are not more than the limit. A run that cannot start stays `Pending` with the reason `PeriodBudgetExceeded`, and it does not fail. It starts in the order of creation time when the budget has room or the period ends. A run with a budget of zero or less fails with the reason `Invalid`. The Agent status gets `budget`, the run budget that the key got. A rebuild of the ledger reads the Agents from the API server, and it keeps the budget of each active run past the maximum of 500 in `reserved`. A run with a key and no `status.budget` counts the full limit in a rebuild. A change of `spec.period` keeps the old spend if the old period overlaps the new period. In a namespace with a SpendBudget, a Pending run with a key hash and no `status.budget` fails with the reason `KeyBeforeLedger`. The manager gets `get`, `list` and `watch` on `spendbudgets` and `update` on their status ([#421](https://github.com/mohanraj00/koodam/issues/421)).
- Add `GET /v1/budgets` to the [spend API](docs/spend-api.md#list-budgets). It gives the `SpendBudget` ledger of each namespace of the caller: the current UTC period, the limit, the spend, the reserved budgets, the remaining budget and the waiting runs. The server identity needs `get` on `spendbudgets`. The operations page shows the budgets in a table ([#422](https://github.com/mohanraj00/koodam/issues/422)).
- Publish the spend-api image `ghcr.io/mohanraj00/koodam-spend-api` for each release tag. It is the `spend-api` target of the root `Dockerfile`, and CI builds it on each PR that changes the spend API or the operations page. [docs/spend-api.md](docs/spend-api.md#container-image) has the image ([#406](https://github.com/mohanraj00/koodam/issues/406)).

### Incident controls

- Add the cluster-scoped `Hold` type with its CRD rules: an incident control with the action `Stop` or `Quarantine` on an Agent, a Workspace, an App, an AppVersion or all the workloads of a Profile. The target, the action, the reason and the user are immutable, and `spec.release` can be set one time. The admission policy `koodam-hold` refuses a `spec.user` or a `spec.release.user` that is not the user of the request, a new Hold with a release, and the delete of a Hold with no release. The chart installs the CRD, the policy (with the name `<release>-hold`) and a read-only viewer role. No controller acts on a Hold in this change. [docs/holds.md](docs/holds.md) has the API ([#185](https://github.com/mohanraj00/koodam/issues/185)).

- The controller does the `Stop` action of a Hold. For an Agent, a Workspace, an AppVersion, an App or a Profile, it blocks the gateway key first and then stops the pods with the revoke path of the kind. A Workspace keeps its home PVC and starts again with a new key after the release. The owner of a workload cannot clear the stop. The Hold shows the condition `Held`, and the controller writes `events.k8s.io/v1` events on the workload and on the Hold. The `Quarantine` action shows the reason `Unsupported` until a later change. The controller role gets `get`, `list` and `watch` on Holds, `update` on `holds/status`, and `create` and `patch` on events. With two installs in one cluster, each manager stops the workloads of its own namespaces only ([#185](https://github.com/mohanraj00/koodam/issues/185)).

- The egress proxy does the `Quarantine` action of a Hold. It watches the Holds and the Profiles, and it is not ready until it reads them. It refuses each call of a quarantined pod with the reason `quarantined`, and it ends the open calls and tunnels of the pod when the quarantine starts. It writes a span of the new kind `control`, with the new optional field `by`, when a quarantine starts and ends. The span version stays 2. The proxy gets `get`, `list` and `watch` on `holds` and `profiles` in a new ClusterRole. The controller does not act on a quarantine yet, and the Hold still shows `Unsupported`. [docs/holds.md](docs/holds.md#the-quarantine) has the limits ([#185](https://github.com/mohanraj00/koodam/issues/185)).

### Apps

- `docs/apps.md` describes a rotation of the gateway key of an App with a new version and the drain time, and a kind test shows no failed model call in a rotation of a 2-replica version ([#184](https://github.com/mohanraj00/koodam/issues/184)).
- **Changed from v0.4.0.** With a tenant claim (`apps.claimCheck.tenantClaim`), each model call of an App pod now needs the header `Koodam-Tenant-Token`. The claim check container gives this signed token to the app with each request of a tenant, and the app must send it with each model call. The egress proxy refuses a model call of an App pod with no valid token (status 403, with the typed reason in `Koodam-Reason`), and it sets the customer of the gateway call to the tenant of the token. Thus the code in an App pod cannot select the tenant of a model call. With this value on, each model call of an Agent pod or a Workspace pod gets the reserved customer `koodam-no-tenant`. No tenant can have this label: the claim check refuses a claim with it (`ReservedTenant`, 403), and the gateway client makes no customer limits for it. The new chart value `apps.claimCheck.tenantToken` (default `true`) sets this; `false` gives the behavior of v0.4.0. The proxy gets `get`, `list` and `watch` on `appversions` in each App namespace, to read the public key of the token from the status. [docs/tenants.md](docs/tenants.md#the-tenant-token) has the flow and the limits ([#415](https://github.com/mohanraj00/koodam/issues/415)).
- Add the namespaced `TenantQuota` type with its CRD rules. It gives one tenant label of the signed claim a request limit and a spend limit for each period, and a rate limit. The chart installs the CRD with `apps.enabled`. No controller reads the type in this change. [docs/tenants.md](docs/tenants.md) has the API ([#378](https://github.com/mohanraj00/koodam/pull/378)).
- Refuse a tenant in the claim check container with a typed reason: `UnknownTenant` (403), `TenantQuotaExceeded` (429) and `TenantRateLimited` (429, with `Retry-After`). The container reads the limits of the tenants from a file and keeps one token bucket for each tenant. The answer has the reason in the header `Koodam-Reason`, and the ingress span has it as its `outcome`. No controller writes the limits file in this change ([#379](https://github.com/mohanraj00/koodam/pull/379)).
- Add the gateway customer of a tenant label to the LiteLLM client: make the customer with a budget for each period and a rate, read its spend and its count of model calls in the current period, and delete it. Koodam owns one LiteLLM budget for each tenant label and changes no other budget. No controller calls this code in this change ([#380](https://github.com/mohanraj00/koodam/pull/380)).
- Add the TenantQuota controller. With `apps.enabled`, it makes the gateway customer of each tenant label, reads the spend and the requests of the current period each 30 seconds (`--tenant-usage-interval`), and writes them to the status. The condition `QuotaExceeded` has the reason `TenantQuotaExceeded` when the tenant is at a limit, and each change goes to the manager log. It is `Unknown` with the reason `RequestCountCapped` when the gateway stopped the count of the requests below the limit. Only the oldest `TenantQuota` of a tenant label has an effect. The App role gets rules for `tenantquotas` ([#382](https://github.com/mohanraj00/koodam/pull/382)). A `TenantQuota` cannot have the reserved label `koodam-no-tenant`: the API refuses it, and the controller gives an older object `Ready=False` with the reason `ReservedTenant` and makes no gateway call for it.
- Add the tenant token, which binds a model call of an App pod to the tenant of a request. With `--tenant-token-key-file`, the claim check container signs a token for the tenant of each request and gives it to the app in the header `Koodam-Tenant-Token`. The egress proxy code can accept a model call of an App pod only with a valid token of its AppVersion, and it then sets the customer header of the gateway call to the tenant of the token. A refusal has a typed reason: `TenantTokenNoKey`, `TenantTokenMissing`, `TenantTokenInvalid`, `TenantTokenExpired` or `TenantLabelNotASCII`. No controller makes the key and the proxy command does not read it in this change ([#415](https://github.com/mohanraj00/koodam/issues/415)).
- Add the tenant token key of an AppVersion. With the field `TenantToken` of the claim check configuration and a tenant claim, the controller makes a Secret with the private seed of an Ed25519 key for each AppVersion. Only the claim check container mounts the seed. The public key is in the new field `status.tenantTokenKey` of the AppVersion, and the controller writes it before a pod gets the seed. A pod template cannot use the name of the seed volume. No manager flag sets the field in this change ([#415](https://github.com/mohanraj00/koodam/issues/415)).
- Refuse the gateway key of an AppVersion in a model call of a different pod. With `--tenant-tokens`, the egress proxy reads the hash of the key from the status of each AppVersion. A model call with that key from a pod that is not a pod of the AppVersion gets the status `403` with `Koodam-Reason: AppKeyOutOfPod`. A call with more key texts than the proxy examines, or with headers, a query and a path that are together too long, or with a query value that has an escape that is not valid, gets `KeyScanLimit`. The check is defense in depth: [docs/tenants.md](docs/tenants.md#the-tenant-token) gives the key locations and the limits.
- Give each AppVersion pod the limits file of its tenants. With `apps.claimCheck.tenantClaim`, the controller writes the ConfigMap `kd-<version>-tenants` with each `TenantQuota` that applies to the App: the rate and the burst divided by the replicas of all the versions of the App with a weight, and the mark of a tenant at its quota. A change needs no new pods. The chart values `tenants.defaultQuota.rateLimit` and `tenants.refuseUnknown` set the limit or the refusal (`UnknownTenant`) of a tenant label with no `TenantQuota`, and `tenants.usageInterval` sets the read interval of the use ([#383](https://github.com/mohanraj00/koodam/pull/383)).
- Add `koodam usage --by tenant`. It shows the requests and the spend of each tenant of the Apps of a namespace in the current period, from the status of the `TenantQuota` objects, with a total line ([#384](https://github.com/mohanraj00/koodam/pull/384)).
- Add the chart values `zone.name`, `zone.namespaces` and `apps.sharedResources`, and the design file `docs/zones.md` ([#385](https://github.com/mohanraj00/koodam/pull/385)).
- Refuse a caller of a different zone in the claim check. With `apps.claimCheck.zoneClaim`, a request with a zone claim that is not `zone.name` gets the status 403 and the reason `ZoneMismatch`. `zone.requireClaim` also refuses a token with no zone claim. Each ingress span of an install with a zone has the field `zone` ([#386](https://github.com/mohanraj00/koodam/pull/386)).
- Refuse a model route of a different zone in the bundled gateway. An item of `gateway.bundled.litellm.modelList` can have a `zone`. With `zone.name`, the route list has only the items with no zone or with the zone of the install, and a call for a model name of a different zone gets the status 403 and the reason `RouteOutOfZone` ([#387](https://github.com/mohanraj00/koodam/pull/387)).
- Refuse an egress host of a different zone in the egress proxy. The chart value `zone.egressHosts` gives a zone to a host. A call to a host with a zone that is not `zone.name` gets a denied egress span with the reason `EgressOutOfZone`. If the list has a host of a different zone, a call to an IP address gets the same refusal. Each egress span of an install with a zone has the field `zone` ([#388](https://github.com/mohanraj00/koodam/pull/388)).
- Refuse a placement out of the zone at admission (`ZonePlacement`). With `zone.name`, a ValidatingAdmissionPolicy refuses an AppVersion with a node selector or a node affinity for a zone or a region that is not in `zone.topologyValues`, and an AppVersion that selects a node by its name. With `zone.storageClasses`, it also refuses a volume claim with a different storage class, and the home claim of a new Workspace gets the first class of the list ([#389](https://github.com/mohanraj00/koodam/pull/389)).
- Add the kind test of the tenants and the zones: 2 installs of the chart in one cluster, each with its own zone, one App and 2 tenants ([#391](https://github.com/mohanraj00/koodam/pull/391)).

### Evidence gate

- Pin Nookku 0.6.0 in `internal/evidence/nookku.pin`, with the plugin hashes of the tag `v0.6.0` in `images/nookku/plugin.sha256`. The seam test adds the 3 new gate cases of 0.6.0: a persona set, a second message that passes and a second message that is late. ### Gateway

- Add an optional guard hook to the bundled gateway for instructions in untrusted content (`gateway.bundled.guard`, off by default). It examines the tool replies and the documents of each model request with fixed rules, and it records, marks or blocks a match. It writes one log line with the policy version and a digest for each new block, and no content. It is a tripwire for known forms, not a defense. The [gateway guard](docs/gateway-guard.md) page lists what it cannot detect. The gateway `callbacks` setting is now a list ([#248](https://github.com/mohanraj00/koodam/issues/248)).
- With the guard on, the chart sets `allow_dynamic_callback_disabling: false`, so a request or a key cannot turn off a gateway hook. The hook examines a large block in pieces, so its memory does not grow with the block. `make guard-image-check` runs the hook in the pinned gateway image with docker ([#248](https://github.com/mohanraj00/koodam/issues/248)).

## v0.4.0 (2026-11-20)

The API is `v1alpha1` and can change between tags. The App parts are off by default. [Known limits of v0.4.0](#known-limits-of-v040) lists the open limits.

### Agents

- Add `koodam usage --by cost-group` to show the Agent gateway usage for each saved cost group in a namespace, with a total and notes for Agents with no valid usage ([#337](https://github.com/mohanraj00/koodam/pull/337)).
- Add `spec.costGroups` to the Profile and the Agent label `koodam.dev/cost-group`. The controller checks the value before it makes a key, then saves it in `status.costGroup` and the gateway key metadata. A later label change does not change the group ([#335](https://github.com/mohanraj00/koodam/pull/335)).
- Add `status.runID` to the Agent. It is the UID of the Agent, so it does not change after a controller restart. The agent container has it in `KOODAM_RUN_ID` ([#315](https://github.com/mohanraj00/koodam/pull/315)).
- Add `spec.output.path` to the Agent. When the run ends, `status.output` has the SHA-256 digest and the size of this file. A sidecar container of the run pod computes the digest, and the controller never reads the file. [docs/agent-output.md](docs/agent-output.md) has the guide for durable output ([#315](https://github.com/mohanraj00/koodam/pull/315)).

### Apps (not active yet)

- Use the App label `koodam.dev/cost-group` for each new AppVersion key. Check it against the bound Profile, save it in `status.costGroup` and add it to the gateway key metadata ([#338](https://github.com/mohanraj00/koodam/pull/338)).
- Add the namespaced `App` and `AppVersion` types with their CRD rules. The CRDs are in `config/apps/crd/bases`, so the default install and the chart do not install them. ([#294](https://github.com/mohanraj00/koodam/pull/294)).
- Add the AppVersion controller. It makes a Deployment and a Service for each `AppVersion`, with one gateway key that has the daily budget, a scoped Role and traced egress. The pod reads the key from the read-only file `/etc/koodam/gateway/key`. A delete or `lifecycle: Retiring` blocks the key before the controller deletes an object. The controller is off by default. To use it, apply `config/apps/crd` and `config/apps/rbac`, and start the manager with `--apps-enabled`. The endpoints, the traffic weights and the admission check are not in this change. The condition `TracedEgress` of an AppVersion is `False` with the reason `NoEgressPolicy`, because no NetworkPolicy selects the App pods before #183. One block response of the gateway is the fence of a revoke. A gateway with more than one replica or worker keeps the auth cache window after the block, as for an Agent and a Workspace (#192) ([#307](https://github.com/mohanraj00/koodam/pull/307)).
- Add the endpoints of an `App` (`spec.endpoints`) and the App controller. Each endpoint names a Gateway API `Gateway`, a port name and a weight for each `AppVersion`. The controller makes one `HTTPRoute` with the name `kd-<app>.<endpoint>`, and the backend weights send the traffic to the Service of each version. Koodam has no router: the Gateway API implementation of the cluster moves the traffic. A version that is retiring, is not bound to the App or has no Service gets the weight 0. `status.endpoints` has the weights in effect and the route state. The controller starts on a cluster with no Gateway API, and then the route state is `NoGatewayAPI`. Session affinity, the drain of a retiring version and the kind test are not in this change ([#308](https://github.com/mohanraj00/koodam/pull/308)).
- Add a default-deny NetworkPolicy for the pods of each `AppVersion`. The policy permits no ingress by default. With `--app-ingress-namespaces`, the pods of these namespaces can send traffic to the ports of the app container. Use the namespace of the Gateway data plane. The egress is the pods of the egress proxy only. The manager makes the policy if it has `--egress-proxy-ip`, `--egress-proxy-namespace` and `--egress-proxy-pod-labels`, and then the condition `TracedEgress` is `True`. An App pod has no direct path to the API server with this policy ([#308](https://github.com/mohanraj00/koodam/pull/308)).
- Keep a client session on one version with the header `Koodam-App-Version`. The route of an endpoint has one rule for each version with a match on this header. A request with the header and the name of a version goes to that version only, if the version has a weight of more than 0 in the spec. A retiring version with such a weight keeps its rule for the drain time. A version with the weight 0 is not open to a caller, also while it retires. The app container has the name of its version in `KOODAM_APP_VERSION`. Gateway API session persistence is not in the standard channel of Gateway API v1.4.0, so Koodam does not use it. An endpoint has 15 versions at most ([#310](https://github.com/mohanraj00/koodam/pull/310)).
- Drain a retiring version before the revoke. With `lifecycle: Retiring`, the version gets no new session, and it keeps its key and its pods for `spec.drainSeconds` of the App (default 300). A session with the version header stays on the version in this time. Then the controller blocks the key and deletes the objects. Koodam cannot see a session, so the end of the drain time is the end of the sessions. A delete of the AppVersion does not wait. The conditions `TrafficAllowed` and `SessionsEnded` show the state ([#310](https://github.com/mohanraj00/koodam/pull/310)).
- Add `apps.enabled` to the chart. If it is true, the chart installs the App CRDs and the App role, and the manager runs the App controllers. With the egress proxy, the manager gets the selector of the proxy pods, and the policy of the proxy permits the App pods. The default is false. [docs/apps.md](docs/apps.md) has the use ([#311](https://github.com/mohanraj00/koodam/pull/311)).
- Add a kind test for the thin App. One App serves 2 versions with a split through Envoy Gateway, a header keeps a session on one version, and a retiring version drains before the revoke ([#311](https://github.com/mohanraj00/koodam/pull/311)).
- Add a `ValidatingAdmissionPolicy` for the AppVersion, in `config/apps/admission` and in the chart with `apps.enabled`. It refuses a change of `spec.template` after the version has a gateway key. It also refuses a name that is not a DNS label with 60 characters or fewer, and a port of the `app` container with no name, a protocol that is not TCP or a host port ([#312](https://github.com/mohanraj00/koodam/pull/312)).
- An `AppVersion` accepts `template.models`, a list of gateway models. The controller makes one key that permits each model of the list. `template.model` stays as the short form of a list with 1 item. The `app` container gets the list in `KOODAM_GATEWAY_MODELS` ([#313](https://github.com/mohanraj00/koodam/pull/313)).
- `template.model` and `budgetPerDay` are optional in an `AppVersion`. A version with no model gets no gateway key, no key Secret and no key alias in the status. It still gets its Role, its Service and its traced egress ([#313](https://github.com/mohanraj00/koodam/pull/313)).
- An `Agent` accepts `spec.models`, a list of gateway models. The controller makes one key that permits each model of the list, and the first model is the model of the harness. `spec.model` stays as the short form of a list with 1 item. An Agent has one of the two forms ([#314](https://github.com/mohanraj00/koodam/pull/314)).
- A `Workspace` accepts `gateway.models`, a list of gateway models. The controller makes one key that permits each model of the list, and the first model is the model of the harnesses. `gateway.model` stays as the short form of a list with 1 item. If the list changes, the controller blocks the key and makes a new key ([#326](https://github.com/mohanraj00/koodam/pull/326)).
- A `TestKey` accepts `spec.models`, a list of gateway models. Each model must be in the gateway of the Workspace. With no list, the key permits only the first model of the Workspace. The slot has a new file `models`, a JSON list of the permitted models ([#327](https://github.com/mohanraj00/koodam/pull/327)).
- The `status.usage` of a `TestKey` and of an `Agent` has a new list `models`. It has the spend, the calls and the tokens for each model of the key that has a call ([#328](https://github.com/mohanraj00/koodam/pull/328)).
- `make manifests` writes the App grants to `config/apps/rbac/role.yaml`. The default role and the chart get no App grant ([#294](https://github.com/mohanraj00/koodam/pull/294)).
- Add the signed claim check at the ingress of each App. With `apps.claimCheck.issuer` in the chart, each AppVersion pod gets the container `koodam-claim` in front of the `app` container. It accepts a JWT of the issuer with RS256 or ES256, and it checks `iss`, `aud`, `exp` and `nbf` with the keys of `apps.claimCheck.jwks`. A request with no valid claim gets the status 401. The `app` container gets the caller label and the tenant label in the headers `Koodam-Caller` and `Koodam-Tenant`, and it does not get the token. The claim check needs `egressProxy.enabled`, because only the NetworkPolicy of a version blocks a call with no claim. The condition `ClaimCheck` of the AppVersion is `True` only if the NetworkPolicy of the version exists and the controller applied the objects of the version ([#316](https://github.com/mohanraj00/koodam/pull/316), [#317](https://github.com/mohanraj00/koodam/pull/317), [#318](https://github.com/mohanraj00/koodam/pull/318), [#319](https://github.com/mohanraj00/koodam/pull/319)).
- The admission policy of the AppVersion refuses `template.rules` on a create and on a template change. The NetworkPolicy of an App pod has no path to the API server, so a version Role has no effect. [#340](https://github.com/mohanraj00/koodam/issues/340) adds this path ([#341](https://github.com/mohanraj00/koodam/pull/341)).

### Nookku preset

- If a harness selects `nookku`, the controller adds the init container `koodam-nookku-python` to the Agent Job pod and to the Workspace pod. It uses the image and the user of the harness container, and it fails with a fixed message if `python3` is absent or older than 3.10. An Agent run fails, and a Workspace pod stays in its init step. [docs/nookku-preset.md](docs/nookku-preset.md) has the requirement ([#366](https://github.com/mohanraj00/koodam/pull/366)).
- Add the Nookku data image definition in `images/nookku`. It has the pinned Nookku 0.5.9 wheel content and plugin files, with a SHA-256 check of each, and a launcher. It has no shell and no Python ([#368](https://github.com/mohanraj00/koodam/pull/368)).
- Add the flag `--nookku-image`. The reference needs a digest. If a harness selects `nookku`, an init container copies the pinned Nookku files from this image into the pod, and `nookku` is on the `PATH` of the harness. With no flag, an Agent with `nookku` fails, and a Workspace has `Harnesses=False` with the reason `NoNookkuImage`. ### Known limits of v0.4.0

- The AppVersion controller has no watch on NetworkPolicy. If a user deletes or changes the policy of a version or of a gate pod, the controller restores it at the next reconcile ([#359](https://github.com/mohanraj00/koodam/issues/359)).
- A valid signed approval record does not show that it is the current selection. A later reject, a suspension or a new snapshot can replace it, and only the Host answers that ([#364](https://github.com/mohanraj00/koodam/issues/364)).
- With the signed claim check on, the gate pod has no claim, so each gate message gets a refusal and the gate gives `Evidence=False/Failed` ([#354](https://github.com/mohanraj00/koodam/issues/354)).
- The plugin preset for Nookku in the harness pod has the Python check and the copy of the pinned Nookku 0.5.9 files from a data image that you give with `--nookku-image`. No published data image exists yet. The proofs with a real harness are not done ([#83](https://github.com/mohanraj00/koodam/issues/83)).
